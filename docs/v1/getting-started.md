# Getting started

There are two setups here, and they share almost nothing. Pick the one that matches what you
are doing:

| You want to | Setup |
| --- | --- |
| build your own documentation locally, to work on templates, styles or scripts before you publish it | [Build your site locally](#build-your-site-locally) |
| change commondoc itself | [Work on commondoc](#work-on-commondoc) |

## Build your site locally

This is the GitHub Pages setup with GitHub taken out of the way. The action runs a container
built from this package, and building locally runs the same image with the same configuration
file and the same command, so a page that builds here builds there. What the local run adds is
a folder you can open and a loop short enough to work on a layout in.

### What you need

Docker, and nothing else: no PHP, no Composer, no clone of this package.

Running the console directly is not the shortcut it looks like. The entry point belongs to
`webware-console`, requires a `config/container.php` in the project it runs from, and exits
when there is none. A documentation repository has no such file, and this package ships no
binary, so the image is the local path.

The image is published at `ghcr.io/common-doc/commondoc:1`. Until that package is public, build
it from a checkout of this repository and use the local tag in its place:

```bash
git clone https://github.com/common-doc/commondoc.git
docker build -f commondoc/docker/Dockerfile -t commondoc:local commondoc
```

### The repository you need

This is the repository that publishes the site, not one of the repositories being documented.

```text
<site repo>/
  commondoc.config.php            the site, in one file
  templates/site/document.phtml   a template, never published
  templates/site/layout.phtml     a template, never published
  theme/site/css/site.css         theme files, published at /theme/site/css/site.css
```

A template is read at render time and its output is written, so it is never published. The
build asks for two of them on every page, `commondoc::document` for the body and
`commondoc::layout` for the shell around it, and two more where it needs them,
`commondoc::home` for a generated home page and `commondoc::redirect` for a component's own
address. Each is replaced by naming it under `theme.themes`, and the fallback is per name, so
a site that replaces the layout and leaves the body alone gets exactly that.

Theme files are published, because a browser fetches them, and they are published by mounting
the theme directory as a source root of its own at `/theme/`. That works because a composed
site has no root at `/`: its component sources are mounted at `/component/v{major}/` and its
home page is generated by the build.

A site that publishes Markdown of its own at `/` cannot also mount `/theme/`, because the two
overlap and are refused. In that shape the theme has to sit inside the root mounted at `/`,
which is the one case where theme files belong among the documents.

### The configuration file

One PHP file returning an array. The image copies it to
`/app/config/autoload/commondoc.global.php` before the command runs, which is how a site
supplies its own roots, target, output, base path and theme.

```php
<?php

declare(strict_types=1);

use CommonDoc\Output\PathType;
use CommonDoc\SiteConfig;

return [
    'view_helper_config' => [
        // '/' for a local server at the root of this host.
        'base_path' => '/',
    ],
    'theme' => [
        'active' => 'site',
        'themes' => [
            'site' => [
                'commondoc::document' => '/github/workspace/templates/site/document.phtml',
                'commondoc::layout'   => '/github/workspace/templates/site/layout.phtml',
            ],
        ],
        'assets' => [
            'site' => [
                'site.css' => 'css/site.css',
            ],
        ],
    ],
    SiteConfig::class => [
        'pathType'    => PathType::Directory,
        'output'      => '/github/workspace/build',
        'roots'       => [
            ['path' => '/github/workspace/theme', 'mount' => '/theme/'],
            // One entry per documented repository, or one organization entry in place of
            // them. See site configuration.
            ['path' => '/github/workspace/components/core', 'mount' => '/core/'],
        ],
        'projectName' => 'My documentation',
    ],
];
```

`/github/workspace` is where your checkout is mounted. Every path in this file is read inside
the container, so it has to be the container's path rather than yours.

The `theme` block is optional, and it is the part that matters while you work on appearance. A
template name mapped to a file replaces the packaged template of that name, and an asset name
mapped to a relative path is served under `/theme/<theme>/`. `commondoc::document` is rendered
with `documentBody` and `page`, and `commondoc::layout` with `content`, which is the body
template's output. [Theme and templates](reference/theme.md) covers the per-name fallback, the
asset map, and every variable each template receives.

`SiteConfig` describes the site: what to read, where to publish, and how a path becomes a file.
`pathType` decides whether a page is written as `<page>/index.html` or `<page>.html`. [Site
configuration](reference/configuration.md) covers composing several repositories into one
site, and the mount each one publishes at.

### Build it

```bash
docker run --rm \
  -e COMMONDOC_CONFIG=/github/workspace/commondoc.config.php \
  -v "$PWD:/github/workspace" \
  ghcr.io/common-doc/commondoc:1 \
  --output /github/workspace/build
```

Pass at least one argument. With none, the image runs its default command, which is the
console's help rather than a build.

A successful run exits `0` and prints one line per file written. A run that recorded a failure
prints one line per failure, with the reason, and exits `1`; the documents that did render are
still written.

The output directory is created as needed and cleared before the build writes, so it describes
this build rather than every build ever run into it. Nothing outside it is touched.

### Look at it

The output is a folder of static files, so any static file server will serve it:

```bash
php -S 127.0.0.1:8080 -t build
```

Then open `http://127.0.0.1:8080/`. `/core/` and `/theme/site/css/site.css` resolve beside it,
and the search box reads `/search-index.json`. Rebuild in another terminal and reload: the
server reads the files from disk on every request. Without PHP on the host,
`python -m http.server` run from inside `build` serves the same tree.

The base path has to be `/` for this, which is the value above. A project site published at
`/<repository>/` states that there instead, and then the root of a local server cannot serve
it.

### Relative paths resolve inside the image

The entry point changes directory to the project root it derives from the autoloader, which
inside the image is `/app`. A relative path anywhere in this setup therefore means something
under `/app`, which is the image's own tree. Stated as `docs`, a root resolves to `/app/docs`
and builds this package's documentation instead of yours, with no error, which is why every
path above is absolute.

## Work on commondoc

This setup changes the package. It needs the source, the test suite, and the four static
analysis gates.

### What you need

- git
- either Docker, which carries the whole toolchain, or PHP 8.4 or newer with `ext-curl`,
  `ext-json` and `ext-mbstring`, plus Composer

### Install

```bash
git clone https://github.com/common-doc/commondoc.git
cd commondoc
composer install
```

With Docker and no host PHP, use the toolchain container instead, so that every command below
runs inside it:

```bash
docker compose up -d
docker compose exec tooling composer install
```

and put `docker compose exec tooling` in front of each command in this section.

### The gates

Four Mago gates have to be clean, and the suites have to pass:

| Command | Runs |
| --- | --- |
| `mago fmt` | rewrites what it can format, so run it first |
| `mago lint` | the linter |
| `mago analyze` | the analyser |
| `mago guard` | the architecture rules |
| `composer test` | the unit suite |
| `composer test-integration` | the integration suite, which builds real corpora |
| `composer mutation-test` | Infection, with both MSI gates at 95 |

On Windows use `bin\mago.bat` in place of `mago`. Infection prefixes `PHP_BINARY` to the
analyser unless it finds a `.bat`, so the shim is what keeps it from running the native binary
through PHP.

Fix a finding at its source. A suppression is a decision, so it carries a reason beside it.

### Build this repository's own documentation

The package's default configuration reads `docs/v1` and publishes at `/`, so a run with no
argument builds the documentation you are reading:

```powershell
php vendor/bin/webware commondoc:build
```

That writes `build/`, which is gitignored. `--output` writes it anywhere else.

On Windows, name the interpreter. `vendor/bin/webware` is Composer's generated proxy, an
extensionless file whose first line is a `#!/usr/bin/env php` shebang, and Windows has no
shebang handling:

```powershell
php vendor/bin/webware commondoc:build
```

### Preview a build in a browser

`compose.yml` has a `preview` service that serves `./build` read-only:

```bash
docker compose up -d preview     # then open http://localhost:8080/
docker compose down
```

It is bound to `127.0.0.1` only, so it is reachable from this machine alone. The site's base
path has to be `/`, which is the default. A build run inside the `tooling` container can read
only what is mounted into it, so a site composed from checkouts elsewhere on the host is built
on the host and previewed the same way.

If you delete or replace `./build` rather than rebuilding into it, run
`docker compose restart preview`: the container stays attached to the directory it started
with, and answers 404 until it is restarted.

### Building a composed site locally

A site of several checkouts is built by pointing the configuration at them. State the roots in
a gitignored `config/autoload/*.local.php` rather than editing the tracked default, so the tree
stays clean:

```php
<?php

declare(strict_types=1);

use CommonDoc\SiteConfig;

return [
    SiteConfig::class => [
        'target' => ['docs/{major}.0', 'docs/v{major}'],
        'roots'  => [
            ['repository' => 'C:/checkouts/message-bus', 'versions' => true],
            ['repository' => 'C:/checkouts/webware-log', 'versions' => true],
        ],
    ],
];
```

An entry with `versions` publishes every released version of that repository at
`/{component}/v{major}/`. Without it, the entry builds one directory. The `target` may be a
list, tried in order for each tag, which is what lets one site hold repositories whose layout
changed between releases.
